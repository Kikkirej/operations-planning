# Data Model: Shared Data Layer (PostgreSQL + Neo4j)

**Feature**: 002 — Shared Data Layer
**Date**: 2026-05-15

---

## PostgreSQL Data Model

### Bootstrap State (provisioned by this feature)

The `app-postgres` instance is initialised with a single bootstrap SQL script
(`infrastructure/postgres/init/01-init-app-role.sql`). This script runs exactly once on
first container start (when the data directory is empty).

```sql
-- Shared login role; all service roles derive CONNECT privilege from this role.
CREATE ROLE app WITH LOGIN NOINHERIT;

-- Remove default ability for any user to create objects in the public schema.
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

-- Allow the app role to connect to the application database.
-- APP_DB_NAME is set via POSTGRES_DB environment variable (default: app_db).
GRANT CONNECT ON DATABASE app_db TO app;
```

**No service schemas are pre-created by this feature.** Each service is responsible for
creating its own schema and role on startup (via Flyway, Liquibase, or equivalent).

### Per-Service Schema Pattern (convention, not provisioned here)

Each service follows this migration pattern on first startup:

```sql
-- 1. Create a service-specific role inheriting from app.
CREATE ROLE svc_example WITH LOGIN NOINHERIT IN ROLE app;

-- 2. Create the service-owned schema.
CREATE SCHEMA IF NOT EXISTS svc_example AUTHORIZATION svc_example;

-- 3. Restrict public schema access for this service.
REVOKE ALL ON SCHEMA public FROM svc_example;

-- 4. Grant schema-scoped privileges.
GRANT USAGE, CREATE ON SCHEMA svc_example TO svc_example;
```

Service-owned tables then live in `svc_example.*` and are inaccessible to all other roles.

### Entity Primary Key Convention

All entity tables across all services MUST use a UUID primary key generated by the owning
service:

```sql
CREATE TABLE svc_example.orders (
    id          UUID PRIMARY KEY,         -- service-generated UUID (e.g., UUID v4)
    -- ... service-specific columns
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

The database enforces the `UUID` type constraint; UUID generation is the service's
responsibility.

### Cross-Schema Access Policy

| Actor | Schema | Access |
|-------|--------|--------|
| `svc_example` | `svc_example` | FULL (CRUD on its own tables) |
| `svc_example` | `svc_other` | NONE — permission denied |
| `app` role | any schema | CONNECT only (no schema object access) |
| superuser (`postgres`) | any | Full access (ops/admin only) |

## Neo4j Data Model

### Node Model

All entity nodes share a single label: `:Entity`. The only stored property is `uuid`.

```
(:Entity {uuid: "<uuid-v4-string>"})
```

| Property | Type   | Constraint | Description |
|----------|--------|------------|-------------|
| `uuid`   | String | UNIQUE (index enforced by constraint) | Service-generated UUID v4 |

**No other properties are stored on nodes.** Service-specific attribute data lives
exclusively in the service's PostgreSQL schema.

### Node Uniqueness Constraint

Applied once on first Neo4j startup via a one-shot init script:

```cypher
CREATE CONSTRAINT entity_uuid_unique IF NOT EXISTS
FOR (e:Entity) REQUIRE e.uuid IS UNIQUE;
```

This constraint also creates an index on `:Entity(uuid)`, enabling O(log n) UUID lookups.

### Relationship Model

Relationships are typed, directed at storage level (start node → end node), and carry no
payload properties.

```
(:Entity {uuid: "A"})-[:RELATIONSHIP_TYPE]->(:Entity {uuid: "B"})
```

| Attribute | Description |
|-----------|-------------|
| Start node | `:Entity` node identified by the source UUID |
| End node | `:Entity` node identified by the target UUID |
| Type | Service-defined SCREAMING_SNAKE_CASE string (e.g., `BELONGS_TO`, `REFERENCES`) |
| Properties | None — no payload data stored on relationships |

**Directionality at query time**: Services use `MATCH (a)-[r]->(b)` for directed traversal
or `MATCH (a)-[r]-(b)` for bidirectional traversal. The storage direction is determined by
the start/end UUID order supplied at relationship creation time.

### Idempotency Rules

| Operation | Behaviour |
|-----------|-----------|
| `MERGE (:Entity {uuid: $uuid})` | Idempotent — creates node if absent, returns existing node if present (FR-008) |
| Create relationship when source or target UUID node absent | Rejected at application level; Neo4j does not enforce referential integrity natively (FR-009, Decision 7 in research.md) |
| Delete node | `DETACH DELETE` removes node and all its relationship edges atomically (FR-007) |

### Example Cypher Patterns

```cypher
-- Register a UUID node (idempotent)
MERGE (:Entity {uuid: $uuid})

-- Create a directed relationship (after verifying both nodes exist at app level)
MATCH (a:Entity {uuid: $sourceUuid}), (b:Entity {uuid: $targetUuid})
CREATE (a)-[:BELONGS_TO]->(b)

-- Query all relationships for a UUID (directed outbound)
MATCH (a:Entity {uuid: $uuid})-[r]->(b:Entity)
RETURN type(r), b.uuid

-- Query all relationships for a UUID (bidirectional)
MATCH (a:Entity {uuid: $uuid})-[r]-(b:Entity)
RETURN type(r), b.uuid

-- Remove entity and all its edges
MATCH (e:Entity {uuid: $uuid})
DETACH DELETE e
```

## Cross-Store Identity Contract

The UUID is the sole cross-store identity key. A UUID that exists as a record in a
PostgreSQL service schema MAY have a corresponding `:Entity` node in Neo4j. The databases
are not automatically synchronised; each service's application logic is responsible for
registering and removing Neo4j nodes alongside PostgreSQL record lifecycle events.

```
PostgreSQL (svc_example.orders.id = "uuid-X")
                 ↕  service-managed sync
Neo4j (:Entity {uuid: "uuid-X"})
```
